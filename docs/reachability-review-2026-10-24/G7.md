### F1 — Python Dockerfile template has no pointer to the production-start rules, and fails the library's own §8b probe

- **class:** R3 (with an S2 side effect)
- **severity:** Medium
- **file:line:** `skills/sota-python/rules/01-tooling-project-setup.md:273-295` (§9 Docker packaging); counterpart `skills/sota-python/rules/05-security.md:327-374` (§8a, §8b), `:264-275` (§7a)

Key points (rules/01:293-295) list deps-before-source, `--no-dev`, non-root, digest pins, and nothing else. rules/05:363-365 says "switch it off in production as defence in depth: `PYTHON_DISABLE_REMOTE_DEBUG=1`, `-X disable-remote-debug`". rules/05:349-355 says dev servers and `--reload` never serve production, and startup should refuse to boot with debug on. rules/05:273-275 says check whether the runtime runs with `-O`/`PYTHONOPTIMIZE` (Dockerfile `CMD`, entrypoint).
- **trigger quote:** SKILL.md:104, the rules/01 index row: "starting/scaffolding a project; reviewing pyproject/uv/ruff/CI setup; …". Docker is not mentioned. The rules/05 row (SKILL.md:108) fires on "debug switches and dev servers … remote debugger attach (PEP 768)", which describes the switch, not the task.
- **why:** rules/01 §9 is the only Dockerfile in the skill, so it is where a "containerize this service" task ends up. It never points to rules/05 §7a/§8a/§8b, so a builder copies a start command with no remote-debug switch and no production-mode guard. I measured this: I extracted the §9 Dockerfile and ran the rules/05:481 probe over it, and it printed `Dockerfile: no remote-debug switch`. A team that follows the BUILD template is therefore flagged by the AUDIT probe (LOW on 3.14 per rules/05:479).
- **proposed fix:** In rules/01 §9, add `ENV PYTHON_DISABLE_REMOTE_DEBUG=1` (or `-X disable-remote-debug` in `CMD`). Add one bullet pointing to rules/05 §7a/§8a/§8b for the production start command. Add "Dockerfile/container image" to the rules/01 index row.
- **confidence:** high (probe run against the template)
