### F1 — unsafe-wrapper Kani obligation never reaches an audit

- **class:** R2 (with an S1 shape: the absence probe exists for parsers only)
- **severity:** Medium — UNSURE (09 calls the whole file "opt-in per crate, by criticality")
- **file:line:** `sota-rust/rules/09-formal-verification.md:22-23`
- **quote:** "**`unsafe` wrapper** → Miri (rules/03 §4), plus a Kani harness on the *safe* API for panic freedom and pointer validity."
- **trigger quote:** `sota-rust/SKILL.md:70-72`: "Load 09 when proofs are present (audit them as controls that can pass vacuously) **or** when a security-critical crate parses untrusted input (§1 decides whether a missing harness is a finding)."
- **why:** This is the worked example's shape for the second obligation in 09 §1. BUILD reaches it: 03 §4 (03:250-252) points writers of `unsafe` to 09. AUDIT does not. Recon loads 09 only when harnesses already exist or the crate is a parser. An auditor of an `unsafe`-wrapper crate with no harnesses therefore never opens 09. And if they did, the only absence probe is parser-scoped (09:247-248, "Security-critical crate parsing untrusted input with no fuzz target and no Kani harness"). The 03 checklist (03:290-339) checks Miri, fuzz targets and `forbid(unsafe_code)`, not a harness on the safe API.
- **proposed fix:** Add a probe to the `sota-rust/rules/03` Audit checklist: a security-critical crate exposing a safe wrapper over `unsafe` with no `#[kani::proof]` = Low/Medium per 09 §1, then load 09. Add "or wraps `unsafe` behind a safe API in a security-critical crate" to the SKILL.md AUDIT recon load condition. If the obligation is really optional, reword 09:22 from a cumulative obligation to "consider".
- **confidence:** medium

### F2 — checklist cites a §5 measurement that §5 says was not made

- **class:** S3
- **severity:** Low
- **file:line:** `sota-rust/rules/09-formal-verification.md:265`
- **quote:** "(a `flags = ["-Z", "loop-contracts"]` array does not count: §5 measured it enabling nothing)"
- **why:** §5 measured the `flags` array only against `function-contracts`, which gave "the same build error as no flag" (09:169-170). It then says explicitly: "`loop-contracts` and `stubbing` were not measured in that table" (09:170). So the checklist claims a measurement §5 disclaims. The same probe also treats `loop-contracts = true` (the `[package.metadata.kani.unstable]` form) as enabling the feature, and §5 did not measure that either. The probe's pass and fail arms both rest on an unmeasured claim.
- **proposed fix:** In the 09 checklist item "Contract or loop attributes without their feature", say the `flags`-array exclusion is inferred from the `function-contracts` measurement, or measure `loop-contracts` under both forms and record the result in §5's table.
- **confidence:** high

### F4 — FFI binding generation and opaque handles have no probe

- **class:** S1
- **severity:** Medium (a header/layout drift is UB at the boundary)
- **file:line:** `sota-rust/rules/03-unsafe-discipline.md:178-188`
- **quote:** "**Generate bindings, don't hand-write them.** `bindgen` (C → Rust) and `cbindgen` (Rust → C header) keep both sides' sizes and alignments consistent. Regenerate in CI, or diff the committed output against a fresh run so the header cannot drift from the code." and "**Opaque foreign types are distinct Rust types, not `*mut c_void`.**"
- **why:** Checked 03's Audit checklist, 03:288-339. It probes `repr(C)`, inbound restricted types, `core::ffi` widths (03:310-311) and allocator pairing. Nothing checks for hand-written `extern` blocks where `bindgen` would apply, for a CI regenerate-or-diff step, or for `*mut c_void` handles. `git grep -nE 'bindgen|c_void' -- skills/sota-rust skills/sota-c-cpp` returns only the two BUILD sentences and the SKILL.md index row (the index row is the positive control).
- **proposed fix:** Add one item to the `sota-rust/rules/03` checklist. Run `rg -n 'c_void' -t rust` on `extern` signatures (each is an untyped handle). Check for an `extern "C"` block with no `bindgen`/`cbindgen` in `build.rs` or CI, and with no diff-against-fresh-run step. Rate it Medium.
- **confidence:** high

### F5 — FPM runtime user and a non-writable webroot are never checked

- **class:** S1
- **severity:** High (the rule says the violation turns any file-write bug into RCE) — confidence medium
- **file:line:** `sota-php/rules/04-sessions-auth-web-hardening.md:254-257`
- **quote:** "Run PHP-FPM as a dedicated non-root user; app files not writable by that user (a writable webroot turns any file-write bug into RCE); secrets in env/ secret manager, not in webroot files"
- **why:** Checked 04's checklist (04:366-464) and 06's (06:164-196). 04:452-464 checks docroot placement, `limit_extensions`, `cgi.fix_pathinfo` and nginx. 06's FPM item (06:174-176) checks only sizing. 06 §4 restates the rule and points back to 04 for it: "One pool per app, distinct user per pool (also a security boundary, rules/04 §5)" (06:82-83). Nothing checks the pool `user =`/`group =`, a root master with root workers, or write permission on the code tree. `git grep -niE 'non-root|writable' -- skills/sota-php/rules` hits no checklist line.
- **proposed fix:** Add an item to the `sota-php/rules/04` checklist under §5. Check `php-fpm -tt 2>&1 | grep -E '^\s*(user|group) ='` per pool (root = High). Check that pools do not share a user. On the image, `find <app-root> -writable` as the pool user should list only the cache, upload and session directories.
- **confidence:** medium

### F7 — memory-cap checklists accept `RLIMIT_DATA` with no macOS arm

- **class:** S1
- **severity:** Medium
- **file:line:** `sota-sandboxing/rules/02-linux-os-hardening.md:283-288`
- **quote:** "**Not Linux: macOS has no cgroup and accepts no memory rlimit.** `setrlimit` rejects `RLIMIT_DATA`, `RLIMIT_AS` and `RLIMIT_RSS` (`EINVAL`...) ... So only 3 (a container, which on macOS is a Linux VM) and 4 remain there."
- **why:** The skill's own top-10 #6 states it (SKILL.md:116-118). Both checklists that test the memory cap pass `RLIMIT_DATA` unconditionally:
  - 02:350-353: "Memory bounded by cgroup `memory.max` or `RLIMIT_DATA`"
  - 04:296-298: "memory is capped with `RLIMIT_DATA`/cgroup"

  On a macOS host, a C/Go sandbox whose `setrlimit(RLIMIT_DATA)` return goes unchecked has no cap and passes both. For contrast, `sota-python/rules/05-security.md:411` already carries the macOS arm in its probe.
- **proposed fix:** Append to the 02:350 and 04:296 checklist items: "on macOS neither rlimit applies (R7.2b) — require a container or an RSS watchdog, and confirm the `setrlimit` return is checked".
- **confidence:** high
